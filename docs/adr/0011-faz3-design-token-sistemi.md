## Bağlam
Master prompt Faz 3a: "merkezi design token kaynağı, Vuetify teması buna bağlı; mevcut ekranlar değiştirilmeden önce davranışı sabitlenir — yalnızca gerçekten değişecek ekranlar için ve Playwright tabanlı smoke/etkileşim testleriyle; 80/20". Kabul kriteri 5: dört yüzey "aynı design token dili"ni kullanır. `premium-ui-standards` skill'i: renk/spacing/tipografi/radius/elevation/motion hardcode edilmez; motion 150–300 ms, `ease-in-out`/`ease-out`; dark mode her token için tanımlı; kırılımlar <768 / 768–1023 / ≥1024.

Girdiler (`PRODUCT_SURFACES.md` §2.5–2.10, `docs/backlog-detail/backlog-1d.md`):
- Hardcode yoğunluğu: 1.717 hex (118+ dosya), 608 `rgb(a)(`, 2.210 inline `style=`, 4.345 `px`, 248 `<style>` bloğu. Hex'ler yoğunlaşmış: ilk 10 dosya ≈ %25 (`StatisticsComponent` 88, `DetailedExportLogReport` 50, `OrderDetailComponent` 45, `AdminSystemManagementView` 41 …). En sık değerler tailwind-slate paleti (`#E2E8F0` 57, `#94A3B8` 49, `#64748B` 46, `#F8FAFC` 42, `#F1F5F9` 29, `#0F172A` 24, `#1E293B` 22, `#CBD5E1` 17, `#334155` 15) + durum renkleri (`#10B981` 24, `#EF4444` 18, `#F59E0B` 17, `#6366F1` 15, `#FEE2E2` 13).
- `vuetify.ts`: `#13255B`'ten `shadeColor` ile türetilmiş ~17 anahtar + ~28 düz renk anahtarı (toplam ~45 özel anahtar); spacing/tipografi/radius/elevation/motion token'ı YOK. `lightTheme` ~45 özel anahtar, `darkTheme` yalnızca 14 (alt küme).
- Dark mode kapalı: `defaultTheme: 'lightTheme'`, `stores/theme.ts` `toggleTheme` gövdesi yorum satırı — ama `ApplicationBar.vue:345` kullanıcıya bir tema anahtarı gösteriyor (tıklanınca hiçbir şey olmuyor).
- `aria-*`/`role=` 0; `vue-tsc` TS6504 ile kırık (→ `npm run build` şu an düşer; yalnız `vite build` geçer); frontend'de test çalıştırıcısı yok.

**Bu ADR sırasında Vuetify 3.8.12 kaynağında (`node_modules/vuetify/lib/{util/colorUtils,composables/theme}.js`) doğrulanan ek bulgular:**
1. **`danger: 'E53935'` / `info: '00ACC1'` çalışma anında BOZUK DEĞİL:** `parseColor` baştaki `#`'i isteğe bağlı sayıyor (`color.startsWith('#') ? color.slice(1) : color`), 6 haneli değer geçerli RGB'ye çözülüyor. Hata hijyen/tutarlılık düzeyinde (lint, ileride token üretimi, değeri doğrudan CSS'e kopyalayan kod). Gerçek anlam hatası: dark temada `info: '444'` (→ `#444444`, gri "bilgi" rengi).
2. **Gerçek (gizli) bir kırık:** `rgb(var(--v-theme-loginColor))` 9 dosyada 17 kez kullanılıyor (`ExportLogList.vue:47,61`, `AdminView.vue:36,49`, `ClaimListView.vue:39` …) ama hiçbir temada `loginColor` anahtarı YOK → `!important` bildirim hesaplama anında geçersiz olur, tarih seçicilerin arka planı "unset" davranır (görsel etkisi tarayıcıda **doğrulanamadı**).
3. **`variables: {'font-size-root': '9px'|'11px'}` ölü koddur:** Vuetify bunu `--v-font-size-root` olarak yayar ama hiçbir Vuetify CSS'i bu değişkeni okumaz (`vuetify.css`'te 0 kullanım). Gerçek kök boyut `public/assets/css/site.css:2` `html { font-size: 14px }`. (PRODUCT_SURFACES §2.5'teki "etkisi doğrulanamadı" maddesi böylece kapanır: etkisi yok.)
4. **Vuetify 2 kalıntıları yok sayılıyor:** `options.customProperties`, tema içindeki `themes: {duygu1, secondary}` ve dark'taki `duygu1` Vuetify 3 şemasında karşılıksız (hiçbir yerden referans yok, grep).
5. Vuetify her tema rengi için `--v-theme-<key>` (RGB üçlüsü) ve **tüm temaların anahtar birleşimi** için `.bg-<key>`, `.text-<key>`, `.border-<key>` sınıfları üretir; `on-<key>` ön-plan renklerini otomatik türetir; kullanıcı temaları `dark` bayrağına göre Vuetify varsayılan light/dark temasıyla birleştirilir. Sonuç: dark'ta eksik olan bir anahtarın sınıfı VAR ama değişkeni tanımsız → dark'a geçişte o yüzeyler saydamlaşır. "Anahtar kümesi tutarsızlığı" bu yüzden dark mode'u açmadan önce çözülmesi gereken yapısal engeldir.

## Değerlendirilen Alternatifler

### A. Token kaynağı ve üretimi
1. **Style Dictionary (veya Tokens Studio/DTCG JSON) ile üretim hattı** — Artı: endüstri standardı, çok platform çıktısı (iOS/Android/Figma). Eksi: yeni bağımlılık + yapılandırma + JSON'da tip güvenliği yok; bizim tüm tüketicilerimiz JS/CSS (web app, tanıtım sitesi, Faz 4 Tauri kabuğu — aynı Vite/Vue/Vuetify yığını). ~100 token ve 2 çıktı formatı için aşırı mühendislik.
2. **Elle yazılmış tek CSS dosyası (`:root { --… }`) kaynak olsun** — Artı: sıfır araç. Eksi: Vuetify `theme.colors` yapılandırma anında JS değeri ister (CSS değişkeni okuyamaz; `parseColor` hex/rgb bekler) → renkler iki yerde tutulur, tek kaynak ilkesi bozulur; light/dark anahtar eşitliği derleyiciyle zorlanamaz.
3. **TypeScript token kaynağı + ~50 satırlık saf render fonksiyonu → iki commit'li CSS çıktısı (SEÇİLEN)** — Artı: tek kaynak; `Record<SemanticColorKey, string>` tipi light/dark anahtar eşitliğini **derleme zamanında** zorlar; Vuetify teması doğrudan aynı nesneden kurulur; ek bağımlılık yok (çıktı `vite-node` ile üretilir — vitest ile birlikte gelir). Eksi: üretilen CSS'in kaynağla eşzamanlı kalması bir drift testine bağlı.

### B. Göç stratejisi
1. **Büyük patlama** (1.717 hex + 2.210 inline style tek seferde) — Eksi: 118+ dosyada görsel regresyon; characterization'sız ekranlara dokunur (Protokol 13 ihlali); tek haneli ölçekte müşteri değeri orantısız.
2. **Global "aynı değer → primitif değişken" codemod'u** (ör. `#E2E8F0` → `var(--ek-palette-slate-200)`) — Artı: light'ta piksel-özdeş. Eksi: primitifler dark'ta değişmez → dark mode'a hiçbir katkısı yok; anlam (bu `#E2E8F0` kenarlık mı zemin mi?) çözülmez, sonra her yer ikinci kez elden geçer. Net değer düşük.
3. **Kademeli "strangler": önce sıfır-fark token omurgası, sonra öncelik sırasıyla ekran-ekran anlamsal göç + mandal (ratchet) (SEÇİLEN)** — Artı: her adım ölçülebilir ve geri alınabilir; characterization yalnızca taşınan ekranlara yazılır (80/20); mandal yeni borç üretimini sıfırlar. Eksi: P3 ekranlarda borç kalır (bilinçli kabul, dark mode kapısıyla yönetilir).

### C. Dark mode
1. **Faz 3'te kullanıcıya aç** — Eksi: taşınmamış ekranlardaki ~1.700 sabit renk dark zeminde okunmaz hale gelir; "bozuk görünen dark mode" premium standardına aykırı.
2. **Hiç yapma** — Eksi: skill "dark mode her token için tanımlı olmalı, sonradan eklenen tema değil" diyor; token katmanını sonradan ikinci kez açmak daha pahalı.
3. **Token katmanında TAM tanımla, kullanıcı anahtarını sayısal bir kapıya bağla (SEÇİLEN).**

### D. Önyüz testleri
1. **Gerçek backend'e karşı E2E** — Eksi: Redis + local Mongo + egress guard + tenant verisi gerekir; yavaş, kırılgan, veri bağımlı; Protokol 7 (sentetik veri) için ek iş.
2. **Playwright + ağ katmanında sentetik fixture (`page.route('**/api/**')`) + Vitest birim/statik testler (SEÇİLEN)** — Artı: deterministik, backend'siz, PII'siz, Windows'ta hızlı. Eksi: backend sözleşme kayması yakalanmaz (bu Faz 5 uçtan uca yolculuk testlerinin işi; backend contract testleri Faz 2'den var).

## Karar
Tek kaynak **TypeScript token modülüdür** (`frontend/src/design/tokens/`, framework'ten bağımsız, Faz 4'te `packages/ui-kit`'e `git mv` ile taşınır); Vuetify teması bu modülden kurulur, geri kalan her şey `--ek-*` CSS değişkenleriyle tüketilir; göç **sıfır-fark omurga → öncelikli ekranlarda anlamsal göç + mandal** şeklinde kademelidir; dark mode token katmanında tam tanımlanır ama kullanıcıya **sayısal bir kapıyla** açılır; testler **Vitest (birim/statik) + Playwright (ağ-mock'lu smoke/etkileşim/ekran görüntüsü/axe)** ile kurulur ve `vue-tsc` kırığı her şeyden **önce** giderilir.

### Karar 1 — Token mimarisi

**Konum ve bağımlılık kuralı**
```
frontend/src/design/
  tokens/                 (SAF TS — vue/vuetify/`@/` import'u YASAK; Faz 4'te packages/ui-kit/tokens'a taşınır)
    palette.ts            primitifler (yalnızca token dosyaları içinde kullanılır, bileşenlerde ASLA)
    semantic.ts           light + dark renk haritaları: Record<SemanticColorKey, string>
    legacy.ts             mevcut ~45 Vuetify anahtarı: light = BUGÜNKÜ BİREBİR değer, dark = eşlendiği semantik token
    scale.ts              space / radius / font / shadow / motion / breakpoint
    render.ts             renderTokenCss(target: 'app' | 'static'): string   (saf fonksiyon)
    index.ts
    dist/tokens.app.css   (üretilmiş, commit'li)   dist/tokens.static.css (üretilmiş, commit'li)
  vuetify-theme.ts        tokens → { lightTheme, darkTheme } (Vuetify adaptörü; tek bağımlılık yönü tokens ← adaptör)
frontend/scripts/build-tokens.ts   (`npm run tokens` = vite-node ile dist/ dosyalarını yazar)
```
- `plugins/vuetify.ts` yalnızca `vuetify-theme.ts`'i import eder; `shadeColor` ve tüm sabit değerler tokens'a taşınır. `main.ts` `tokens.app.css`'i global olarak import eder.
- **İki çıktı:** `tokens.app.css` renkleri Vuetify'a bağlar (`--ek-color-border-default: rgb(var(--v-theme-border-default))`) → tema değişimi tek noktadan (Vuetify `.v-theme--*` sınıfı) akar. `tokens.static.css` aynı adları **literal** değerlerle `:root` (light) ve `[data-theme="dark"]` altında yayar → Vuetify'sız tüketiciler (tanıtım sitesi) için. Drift testi: commit'li dosya ≠ `renderTokenCss()` çıktısı ise test kırılır.

**İsimlendirme şeması**
- CSS değişkeni öneki **`--ek-`** (Entegrasyonik). Çakışma kontrolü yapıldı: `src/`/`public/` içinde `--ek-` 0 kullanım; Vuetify `--v-*`, tanıtım sitesinin `--accent`/`--w50`, `legal.css`'in `--primary-color`'ı ve bileşenlerdeki `--brand-color`/`--mode-color` ile ad alanı ayrık.
- Biçim: `--ek-<kategori>-<rol|ölçek>[-<varyant>]`, kebab-case. Vuetify tema anahtarları da **kebab-case** (Vuetify'ın kendi `surface-variant`, `primary-darken-1` konvansiyonu); mevcut camelCase anahtarlar yalnızca `legacy.ts`'te yaşar.
- **Yasak anahtar adları** (Vuetify'ın `.text-<key>/.bg-<key>/.border-<key>` üretimiyle yardımcı sınıflara çarpar): `h1…h6`, `subtitle-*`, `body-*`, `caption`, `overline`, `button`, `center`, `left`, `right`, `start`, `end`, `justify`, `truncate`, `wrap`, `no-wrap`, `uppercase`, `lowercase`, `capitalize`, `sm`, `md`, `lg`, `xl`, `thin`, `opacity-*`, `on-` önekiyle başlayan her şey (Vuetify `on-*`'ı kendisi üretir). Birim test kara listeyi zorlar.

**Vuetify ile entegrasyon**
- `theme.themes.{lightTheme,darkTheme}.colors` ← `vuetify-theme.ts` (semantik + legacy birleşimi). Tema adları `lightTheme`/`darkTheme` **korunur** (`stores/theme.ts` ve `ApplicationBar` bunlara bağlı).
- Silinecek ölü yapılandırma: `options.customProperties`, iç içe `themes`/`duygu1`, `variables.font-size-root` (Bağlam 3–4 — davranış değişmez).
- `theme.variables`: yalnızca Vuetify'ın gerçekten okuduğu değişkenler (`border-color`, `*-opacity`) token'dan beslenir.
- **`defaults` (bileşen varsayılanları) omurga adımında BOŞ kalır.** VBtn/VCard/VTextField varsayılanını değiştirmek her ekranı aynı anda değiştirir (gizli büyük patlama). Her `defaults` girdisi ayrı bir commit'tir ve P1 ekran görüntüsü tabanına karşı bilinçli yeniden-taban (re-baseline) ile girer.
- **Vuetify SASS `configFile` AÇILMAZ** (radius/tipografi SASS değişkenleri): `autoImport` ile her bileşen stilini yeniden derletir, build süresini belirgin uzatır; ihtiyaç `defaults` + `--ek-*` ile karşılanır.
- **`display.thresholds` omurgada DEĞİŞMEZ** (sm 600 / md 960 kalır). 768/1024'e hizalama 710 grid kullanımının yerleşimini aynı anda değiştirir → ayrı, tek commit'lik "kırılım hizalama" görevi, P1 ekranlarının 3 viewport ekran görüntüsü tabanı varken yapılır.

## Maliyet/Ölçek Notu
- **Ek maliyet:** ~4 devDependency; Playwright Chromium indirimi (~150 MB, faz kapanışında Firefox/WebKit ek); ekran görüntüsü tabanları repo'da (P1 × 3 viewport × 2 tema ≈ 60–80 PNG, birkaç MB). Operasyon yükü: token değiştiğinde `npm run tokens` (drift testi unutmayı yakalar).
- **Yeniden değerlendirme eşikleri:**
  - Token tüketicisi **4 farklı çıktı formatını** aşarsa (ör. native iOS/Android, Figma senkronu) **veya** token sayısı **300'ü** geçerse **veya** tasarım token'ları bir tasarımcı tarafından Figma'da yönetilmeye başlarsa → Style Dictionary/DTCG geçişi ADR'si.
  - Playwright ekran görüntüsü testleri ardışık **20 koşuda %5'ten fazla** kararsız (flaky) sonuç verirse → piksel karşılaştırması P1 kabuk + giriş ile sınırlanır, diğerleri DOM/rol doğrulamasına indirilir.
  - Faz 3 sonunda toplam literal renk sayısı **1.000'in** üzerinde kalır **ve** dark mode açılışı P3 yüzünden ertelenmişse → P3 için Seçenek B2 (aynı-değer codemod) + ekran bazlı zorla-light yeniden değerlendirilir.
  - `vue-tsc` hata mandalı **2 hafta** boyunca düşmezse veya P1 dosyalarında 0'a inmezse → `vue-tsc` 2.x yükseltmesi/`strict` ayarı ayrı görev olarak öne alınır.
  - Vuetify `defaults` + `--ek-*` ile **3'ten fazla** bileşende hedef radius/tipografi elde edilemezse → SASS `configFile` (build süresi ölçülerek) yeniden değerlendirilir.
  - En az **2 ödeyen müşteri** dark mode talep ederse → dark kapısı öncelik sırası yeniden değerlendirilir (P1+P2 göçü öne çekilir).
